# 2026-11-16 장비 확인 및 수집 기록

## 자료와 진행 결과

학교 `3.Dofbot조작_라즈베리파이5.pdf`와 `4.Dofbot_Data수집_라즈베리파이5.pdf`를 확인했다. 제조사 Docker 안에 조작 노트북, JupyterLab, ipywidgets, Arm_Lib, OpenCV가 있었다. PDF 수집 코드는 이미지에 포함된 코드를 옮겼다.

처음에는 Docker Jupyter에서 학교 방식을 준비했다. 이후 사용자가 게임패드·USB 카메라·CSI 카메라를 모두 Pi에 연결한 상태로 조작하기를 요청해, 호스트 `.venv`에서 직접 입력을 읽는 `data_collect.py`를 작성했다. Docker Jupyter 방식과 현재 실행 스크립트는 별도 경로다.

현재 경로는 게임패드 직접 입력 → 목표각 명령 → USB/CSI 프레임 수신 → 이미지·CSV 저장이다. 학습·추론·자동 집기 코드는 이번 변경에 포함하지 않는다.

## 실물에서 확인한 것

| 항목 | 관찰 |
| --- | --- |
| 보드 | Raspberry Pi 5, Debian Bookworm, Python 3.11 호스트 |
| Arm_Lib | 시스템 Python에는 없고 저장소 `.venv`에는 있음 |
| I2C | `/dev/i2c-1`, 이동 없이 6개 각도 읽기 성공. 당시 약 24~28ms/회 |

| USB 카메라 | Sonix/Microdia. 지원 최대 640×480 YUYV, 디지털 줌 제어 항목은 없었음 |
| CSI 카메라 | OV5647. 리본 케이블 재연결 후 센서 인식은 됐지만 촬영 timeout 발생 |
| CSI 복구 | 사용자 요청으로 정상 종료·재부팅 후 공식 `rpicam-still` 사진 저장 성공 |
| 두 영상 | 수집 화면에서 USB·CSI 640×480 JPEG 수신을 각각 확인 |
| 실제 저장 | 한 세션에서 USB 이미지 21장 + CSI 이미지 21장 + CSV 21행 확인, 저장 이미지 크기는 244×244 |
| 종료 저장 | 재부팅 전 별도 USB 단일 카메라 세션에서 358프레임 종료 메타데이터 확인 |

위 수량은 특정 확인 시점의 스냅샷이다. 전체 데이터셋 수량·장시간 안정성·집기 성공률을 의미하지 않는다. 실제 물체 이동, 전 관절의 버튼 매핑·방향은 조작자가 추가 검수해야 한다. 최종 GitHub 커밋 그대로의 장시간 실물 시험은 수행하지 않았다.

## 연결 끊김: 확인과 미확정 사항

- 수집 화면이 끊겼을 때 SSH도 응답하지 않고 Tailscale에서 Pi가 오프라인인 경우를 여러 번 확인했다. Mac 쪽 Tailscale은 실행 중이었다.
- 사용자가 껐다 켰다고 명시했다. 따라서 반복된 낮은 uptime을 자동 재부팅 증거로 해석하면 안 된다.
- 커널에 `Undervoltage detected!`와 정상화 메시지가 반복됐고 `get_throttled=0x50000`을 확인했다. 이 값은 저전압·스로틀링 이력이며 조회 순간 지속 여부는 별개다.
- 끊김 원인이 Wi-Fi, 전원, Tailscale 중 무엇인지는 확정되지 않았다. 중단된 상태에서는 Pi 내부 수집이 계속됐는지도 확인할 수 없었다.
- 마지막 확인들에서 `eth0`은 DOWN, `wlan0`은 UP이었다. 공유기 유선 또는 노트북↔Pi 유선 직결을 제안했지만 실제 적용·검증하지 않았다.

네트워크가 끊기면 모터도 반드시 멈춘다고 가정하지 않는다. 현재 입력은 Pi에 연결된 게임패드에서 직접 들어온다. 장비 옆에서 START로 정지하고, 세션 파일을 확인한다.

## 장치 번호·점유

USB 카메라는 어떤 부팅에서는 video8, 다른 부팅에서는 video0이었다. CSI의 libcamera 인덱스 0은 `/dev/video0`과 같은 의미가 아니다. 그래서 현재 스크립트는 USB의 by-id 경로와 Picamera2 CSI 인덱스를 사용한다.

제조사 `YahboomArm.pyc`가 자동 실행되어 카메라를 점유했다. 정확한 프로세스를 확인해 종료하고 수집을 재실행했다. 이 초기 점검에서는 Docker 컨테이너를 종료하지 않았다. 제조사 앱의 자동 시작 설정은 변경하지 않았으므로 재부팅 후 다시 확인해야 한다.

### 2026-11-16 후속 재부팅 점검

재부팅 뒤 `Camera 0 ... gave no frame`이 다시 발생했다. `fuser`에서 USB 카메라 소유자로 `YahboomArm.pyc`를 확인했다. 이전에 보았던 Docker 컨테이너 이름은 이미 종료된 컨테이너였고, 재부팅 후 새 이름으로 실행된 컨테이너가 카메라를 점유하고 있었다. `docker ps`와 `docker top`으로 현재 컨테이너를 식별한 다음 그 컨테이너를 중지했고, 이어진 점유 조회에서는 `/dev/video0` 소유자가 보이지 않았다. 컨테이너 중지는 10초 뒤 강제 종료(종료 코드 137)로 끝났다. 자동 시작 설정은 바꾸지 않았다.

이후 SSH 연결이 시간 초과되어 수집 프로그램의 재시작 결과는 확인하지 못했다. 따라서 카메라 해제 후 수집이 정상 시작됐다고 기록하지 않는다. 다음 실행은 `fuser`에서 점유가 없음을 확인한 뒤 다시 검증해야 한다.

Tailnet 공유를 위해 Pi에서 Tailscale Serve를 활성화하고 `127.0.0.1:8081` 프록시를 설정했다. Serve는 Tailnet HTTPS 주소를 출력했지만, 이후 브라우저에서 실제 수집 화면과 게임패드 동작까지 확인하지는 않았다.

## 영상 시야·데이터 한계

웹 화면은 받은 640×480 프레임 전체를 축소 표시하며 별도 crop·디지털 줌을 하지 않는다. CSI는 Picamera2가 센서 모드를 선택하며 전체 센서 최대 시야 사용 여부를 별도로 계측하지 않았다. USB는 촬영 위치상 CSI보다 좁은 영역이 보였고 밝은 부분이 과노출된 장면이 있었다. 해상도별 시야 비교·노출 보정·최종 카메라 장착 위치 확정은 남아 있다.

학습 이미지의 244×244 변환은 crop이 아니라 비율을 바꾸는 resize다. 두 카메라는 최신 수신 프레임을 묶으므로 노출 동기화가 아니다. 목표각과 실제 측정 자세도 다를 수 있다. 고정 운반 동작, 학습용 변환, 품질 필터, 성공/실패 자동 판정은 포함하지 않는다.
